# Step 6a.2 Task 3 Slice 4C — private validation startup

**Status: proposed for root review, 2026-09-28. No code or frozen-stream draw is authorized by this document.** This slice follows accepted Slice 4B at `bcaa900` and the [Task 3 contracts](2026-09-27-step6a2-task3-contracts.md), especially §§6–8 as amended by operator decision D29 (same-process completion authority). It connects a completed calibration to a private validation context. It does not run validation, expose a combined command, create official review attestation, or consume a reserved seed.

## Plain-English purpose and boundary

A durable calibration result is evidence, but its candidate file carries no permission to proceed. Slice 4C accepts only the exact live completion object issued in the current process, independently rereads and recomputes the complete calibration evidence, and starts one new validation attempt with the already selected floor. A complete calibration **FAILED** result cannot start validation. A process restart cannot reconstruct permission from files.

The calibration deadline remains the historical two-hour limit that governed calibration through completion; do not reset or extend it. A **single fresh two-hour validation deadline** starts at private validation entry, *before* calibration-trio reverification, Git/attestation rechecks, resource setup, or any validation artifact operation. That one deadline continues into later validation generation, saved-result verification and completion. Do not start another validation deadline at claim creation or at the future draw. The 2 GiB address-space ceiling stays installed and enforced across the handoff; read back its effective hard/soft limits and refuse any mismatch. No calibration deadline check may reject an otherwise valid capability merely because time passed after completion.

## Ownership and minimal API

- Modify only `scripts/signal_calibration.py` and `tests/unit/test_signalcalibration_task3.py` after review. Keep all production implementation private in the protected harness. No new module, persistent state, evidence file, registry, CLI subcommand, public selection artifact, or phase RNG entry point.
- Introduce only `_begin_validation_phase(calibration_context, completion, manifest) -> _PhaseContext`. It derives operations from the authentic calibration context and starts its own deadline; no caller supplies ops, deadline, floor or path. `_begin_linux_phase("validation", ...)` remains a direct-call refusal. The separate handoff path returns a validation context whose canonical identity binds the independently recomputed first-passing floor and completion lineage.
- Add one private, one-shot consumption state to the issuing calibration context. Check exact issued-object identity, issuer marker, original/current PID, context and writer bindings with `_require_phase_completion`; mark consumed **before** any fallible trio read or validation preflight. Every second call refuses before claim or RNG. On any failure, revoke/close both owned contexts and retain any already reserved claim/result/candidate bytes. No retry, replacement, deletion, rename, truncation or resume. This is an accidental-misuse boundary, not a defense against arbitrary code in the issuing process.
- Keep calibration-owned retained claim/result/directory descriptors alive through trio verification and validation claim/result reservation. Track all newly opened candidate readers and validation descriptors with explicit ownership; relinquish ownership *before* a single close attempt even if close releases then raises. Recheck the calibration trio's original device/inode, regular-file/single-link state, exact extent and bytes at the late boundary before returning validation context; close calibration handles only after that check succeeds. A late edit or close error fails the startup and leaves no usable validation context.

## Ordered checks

1. Require native Linux, the authenticated full manifest, exact calibration context and **PASSED** live completion with a non-null first-passing floor. Require the phase's original PID. Consume the capability once. Derive the manifest hash and all calibration/validation paths; accept no caller-selected path or floor. A future user-supplied result path may only locate the derived calibration result and must match it exactly.
2. Establish the one fresh validation monotonic deadline using the authenticated `runtime_limits.max_elapsed_seconds`. Start it immediately at entry before meaningful authority, manifest, trio or preflight work. Cheap identity/PID refusal may precede or follow clock start but cannot delay it. Derive the clock from the authentic context's resource operations and the duration from the authenticated manifest. Its clock must be the same monotonic source used by subsequent validation operations. Reject non-finite, expired or altered duration.
3. Under this **new operational deadline**, freshly verify the exact calibration claim/result/candidate trio through retained no-follow directory handles. Do not mutate the calibration context's original deadline, resource binding, completion payload or historical elapsed snapshot. Reuse the strict saved-result parser/pure `validate_phase_result` and independent expected provenance; make the smallest shared-verifier refactor needed to supply an operational deadline while preserving the original context identity checks. Do not add a second statistical interpretation. Recompute every cell, event partition, confidence bound, parity check, candidate control and the first passing floor. Require `PASSED`, non-null selected floor equal to the completion payload, and exact result hash/size/original identity. Strictly parse the canonical `step6a2-completion-candidate-v2` bytes, require `authority:"NONE"`, and compare every derived field, path, hash, size, verdict, prewrite snapshot bound and original identity to the live completion and verified claim/result. Never treat candidate bytes as authority.
4. Re-run the reviewed-commit ancestry and tracked-byte proof under the validation deadline. The only untracked allowance is frozen `AGENTS.md` plus the **three exact verified calibration paths**; reject extra siblings, prefixes/globs, stale validation paths and committed calibration files. Confirm the exact attestation and protected blobs remain bound. Re-prove native Linux/filesystem support and the effective 2 GiB resource limit; no relaxation of `RLIMIT_AS` or bypass of current VMS/RSS/peak and planned-allocation guards. Refuse before a validation claim if any proof fails.
5. Derive the validation claim/result/candidate paths from the same reviewed commit. Recheck the calibration trio immediately before validation claim reservation, then use the existing exclusive, mode-0600, no-follow, file-plus-directory-fsync startup for the validation claim and result. Validation claim and result remain inert and do not draw RNG. Recheck the trio after claim fsync and again after result reservation using owned readers/descriptors with no double close. The Git allowance is frozen `AGENTS.md` plus the verified trio before reservation; derived validation paths become allowable only once created. Bind the recomputed floor and completion lineage in the validation context's canonical identity. If startup fails after claim reservation, leave that attempt permanently reserved and close owned handles once.
6. No provider is issued and no result writer is activated in this slice. The future validation execution must require this exact live validation context and its bound floor, and must refuse any late change to its own claim or result. The future combined CLI is a separate reviewed slice; an isolated test helper may drive this private handoff with scripted evidence only.
