# Windows official-calibration support: platform design investigation
Date/as-of: 2026-09-30. Status: INDEPENDENTLY REVIEWED FOR INVESTIGATION ONLY; NOT IMPLEMENTATION APPROVAL.

## Plain-language decision
The simulator already works on this Windows PC. The official one-shot experiment also needs the operating system to prevent excess memory use and preserve the evidence of an attempted draw after a crash. Those are separate requirements. Replacing the Linux checks with Windows API names is not enough.

**Recommendation:** approve bounded, test-only capability investigation, and retain the existing Windows refusal for official startup. A Windows official backend is not yet justified. Two blocking gaps remain: an enforceable equivalent of the 2 GiB address-space cap, and a documented, tested durable namespace barrier for claims and newly created evidence directories. No reserved stream, statistical threshold, source manifest, broker path or OS migration is authorized by this draft.

## Existing contract and source boundary
Read the [exact contracts](2026-09-27-step6a2-task3-contracts.md), especially sections 3, 6-9; the [native envelope plan](2026-09-28-step6a2-task3-native-envelope.md); and the [Windows checks](../reviews/2026-09-30-windows-simulator-check.md). Inspected implementation: `scripts/signal_calibration.py`, `_prepare_linux_resource_boundary`, `_NativeLinuxOps`, `_PhaseContext`, secure evidence reservation, finalization and combined CLI.

Current startup refuses Windows before claim/context/cache/RNG. Linux installs and reads back soft+hard `RLIMIT_AS = 2,147,483,648` bytes; peak RSS is separately measured. Each phase has one original 7,200-second monotonic deadline including startup, writing, independent verification, sync, close and completion checks. Validation starts its own clock before fresh calibration verification without resetting process-lifetime memory peaks.

The runner retains no-follow directory/file descriptors, uses exclusive creation and mode 0600, rejects extra hard links and changed identities, syncs file plus containing directory, and syncs a created directory plus its parent. Any failure prevents completion authority. Candidate bytes are inert; only the issuing process's private capability can unlock a passing calibration's validation. A consumed capability is not retryable; process loss destroys continuation.

All tracked transitive source bytes are protected by exact review ancestry. The manifest permits no casually added project-owned backend import. A future Windows implementation must first have a reviewed integrity/provenance plan covering the changed harness and any native launcher/backend; do not silently change the protected code boundary or preserve an obsolete attestation. This draft changes none of it.

## Memory: hard cap versus measurements
Microsoft documents `JOB_OBJECT_LIMIT_PROCESS_MEMORY` and `JOB_OBJECT_LIMIT_JOB_MEMORY` as committed-memory limits; allocation beyond the applicable commit limit fails. CPU-time Job limits measure user-mode execution, not the required elapsed phase time. [Job limit information](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).

`VirtualAlloc(MEM_RESERVE)` can reserve address space without backing storage, whereas commitment is separate. Therefore a 2 GiB committed-memory cap does not establish a 2 GiB reservation/address-space cap. This is an inference from those two documented definitions, not a measured result on this PC. [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc).

Windows `PROCESS_MEMORY_COUNTERS_EX` distinguishes current/peak working set from current/peak private commit. Those counters must be labelled by their actual meanings; neither private commit nor a library field called "vms" can be relabelled as proven total reserved address space. [Process counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex).

Required research: identify a documented hard boundary for the complete worker address-space footprint, installed before any claimed phase begins, read back and kept active through verification/finalization. Test reservation-only growth, committed growth, mapped files, NumPy/native-library allocations and concurrency. A monitor can sample and kill, but transient over-limit allocation between samples is not prevented. A passing resource run is not a proof of enforcement.

**B1 blocking:** no equivalent native Windows hard address-space mechanism has been established. Do not propose a commit-cap amendment as an unnoticed platform port. If equivalence cannot be established, report Windows official support unavailable under this contract. Changing the resource definition would require a separate explicit contract decision, outside this proposal; this draft recommends no such change.

## Secure evidence: handles, paths and identity
A candidate native adapter would hold an authenticated local-volume root and traverse one validated filename component at a time relative to retained parent handles. Microsoft documents `NtCreateFile` with `RootDirectory` for relative opens, `FILE_CREATE` for existing-name refusal, directory/non-directory type restrictions and `FILE_OPEN_REPARSE_POINT`. These provide building blocks, not a completed secure adapter. Documented directory-option combinations and user-mode ABI/status handling must be reviewed before selecting exact flags. [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile).

Ordinary absolute-path `CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT` alone does not prove safe retained-parent traversal. Root authentication must also cover ancestor reparse/mount points. Reject every reparse object rather than trusting only symbolic-link tags. Reject UNC/device paths, alternate data streams, path separators, dot components and case/normalization aliases outside the canonical manifest filenames. No check-then-open sequence may be the security boundary. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

File information exposes link count and volume/file identity. Keep retained handles and recheck identity, exact bytes, extent and link count through reservation, verification and validation handoff; do not treat an ID as permanently unique after deletion. Unsupported observations refuse. [Handle information](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information); [128-bit identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info).

Require a reviewed explicit DACL equivalent to the intended private evidence mode, non-inherited handles and sharing settings compatible with separately owned verification readers while denying conflicting writers/deletion. Existing broad ACL inheritance is not sufficient evidence of privacy. Verify source-cleanliness paths and Git-derived identities with Windows spelling rules. [File security](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights).

Candidate initial filesystem scope is a dedicated local NTFS evidence location, verified from retained handles; reject network, cloud placeholder/reparse, removable or unknown locations unless separately proved. NTFS alone does not prove hardware persistence. The current PC's selected volume/device/ACL/filter-driver configuration has not been audited here. [Volume information by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew).

**B2 blocking pending probes:** exact race-safe open/creation flags, root ancestry, reader sharing, link-count/identity changes, ACLs and one-close ownership behavior require adversarial native tests. Do not reuse POSIX fd assumptions for Windows handles without a reviewed adapter contract.

## Durability: the unresolved namespace barrier
`FlushFileBuffers` documents file-buffer flushing and requires a writable handle. It also describes an administrator volume-handle flush. Its page does not establish the exact retained-parent-directory barrier needed by this runner for durable exclusive claim creation and nested directories. **This is an evidence gap, not a claim that Windows cannot persist directories.** [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

Microsoft's native flush description gives synchronous file flush behavior, but supplies no complete parent-directory namespace ordering contract in the inspected page. Merely replacing `fsync(parent_fd)` with `NtFlushBuffersFile` is unproved. [Native flush](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-zwflushbuffersfile).

Write-through/unbuffered settings deserve investigation but must not be declared sufficient without documenting claim-name and ancestor durability, alignment/partial-write behavior and storage-cache guarantees. File creation metadata can still be cached. Do not introduce rename, overwrite, pre-existing claim files, transactional storage or a new attempt journal as a shortcut to change the one-shot evidence model. [CreateFile caching guidance](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

**B3 blocking:** obtain a documented durability/order argument for file content, extent, exclusive claim name, candidate name and every newly created ancestor on the actual storage stack. Separate application crash from OS crash and power loss. A successful API return or repeated reread is not a power-loss proof. No destructive host power cut, system reboot, volume flush, device-cache setting or administrator privilege is authorized by this draft.

Power-loss risk is particularly consequential: losing the exclusive claim after an attempted draw could make a later process believe the stream unused. Private process-local completion prevents restart continuation; it does not by itself prevent a lost-claim redraw. Until this barrier is established, Windows refuses before claim/RNG.

## Deadline and supervisor proposal
A test-only launcher could create an unnamed Job Object, install/read back the chosen containment flags, create the worker suspended, assign it to the job and verify membership before resuming. No breakaway flags or inheritable/duplicated job handle may let a child escape. All child processes, including source-proof subprocesses, must be accounted for; do not choose a one-process limit incompatible with existing Git checks. The supervisor belongs outside the worker job and owns the last job handle.

Microsoft documents `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` killing associated processes when the last job handle closes. This is a useful crash-containment candidate, not a memory-semantics solution. Validate nested-job behavior when launched from this desktop environment, permission failures and handle leaks rather than assuming membership. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Use the worker's original monotonic phase clock for authority checks, plus an independently supervised deadline for a stuck native call. A watchdog may terminate the job on expiry; forced termination never reports completion and leaves reserved evidence untouched. Microsoft documents `TerminateJobObject` terminating associated processes; it is not graceful evidence finalization. [Job termination](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject).

Do not substitute user-mode CPU-time Job limits or a total two-phase timer for separate 7,200-second phase deadlines. A calibration PASSED handoff must begin a new validation clock before fresh trio verification while preserving the same worker PID/capability. An explicit supervisor protocol must bind phase changes to that private controller; arbitrary child messages cannot reset a timer or certify completion. Worker completion checks remain authoritative even if the supervisor is delayed.

QPC provides interval measurement independently of UTC. A timer is a wakeup aid, not proof of elapsed eligibility. Windows 8+ relative waitable timers exclude low-power time and absolute timers follow system-time adjustments. Review suspend/resume semantics, refuse power-state uncertainty and never extend the frozen budget because a callback was late. [High-resolution time](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps); [Waitable timers](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setwaitabletimer).

**B4 blocking pending probes/review:** suspended startup, job membership, external-supervisor loss, worker deadlock, child escape, nested jobs, timer race and phase handoff must fail closed. Killing a process may leave reserved bytes without a valid result; the operator must understand that before any official attempt.

## Completion and statistical protocol stay fixed
Preserve the exact schema, master seeds, cells, replicates, metric families, parity checks, CP recomputation, candidate-floor order and first-passing rule. Statistical FAILED is a legitimate consumed official outcome, not an invitation to tune this design. Test-only FAILED results cannot predict the untouched reserved streams.

A Windows backend cannot issue completion until all required writes/syncs, one-close attempts, byte/identity checks, verification handles, resource samples and original deadline checks succeed. It issues only the original private live capability in the same PID/context, once. Persisted candidate bytes remain authority NONE. Validation recomputes all passing calibration evidence and consumes capability once before fallible startup; interruption never resumes or redraws.

No supervisor service, database, saved token, reopened candidate, copied Python object or IPC acknowledgement can become new completion authority. Reports must name the actual Windows memory counters and storage barriers rather than claiming Linux `RLIMIT_AS`, inode or directory-fsync evidence.

## Ordered investigation and acceptance
1. **Independent design review now.** Review this draft and its negative conclusions. Establish which exact unresolved mechanisms could satisfy the existing contract. This is not a whole-runner approval or canonical attestation.
2. **Bounded native capability probes, if separately scoped by the orchestrator.** Use disposable scratch evidence only, non-reserved inputs, no credentials/network/broker and no production official paths. Probes may create files/jobs only within their nominated scratch root; no persistent system settings, elevation, reboot or power manipulation. Hard process isolation and bounded time/memory are required so failures cannot exhaust this shared PC. Publish raw API return/status, flags, handle ownership, identity/ACL/volume measurements and source hashes. An operation that succeeds without privilege is not evidence of a stronger durability guarantee.
3. **Resolve B1-B4 before implementation approval.** Probes can disprove an API candidate or establish local capability, but cannot close B1 through polling nor close B3 by rereading cache. Seek stronger primary-source documentation/storage evidence where needed. If no equivalent solution exists, record the official platform blocker and continue Windows fixtures.
4. **Reviewed implementation plan only after the blockers are resolved.** Explain a minimal private backend/supervisor boundary, dependencies, schemas/integrity version changes and native failure injection before requesting build approval. Freeze the exact platform contract before viewing any official statistics. No code or dependency change is implied here.
5. **Implementation acceptance, all test-only.** Red/green failure tests: allocation versus reservation, mapped/native allocations, namespace replacement at every level, reparse roots/children, hard links, ACL leaks, denied sharing, unknown volume, truncated writes, sync failure, close failure, deadline during I/O and after close, supervisor death, claim collision, copied capability, restart and FAILED-calibration validation refusal. Skip means unproved, not passed. Prove claim persistence separately from in-process completion.
6. **Full-size Windows non-reserved resource evidence.** Exercise generated calibration, scripted high-size passing handoff and validation-fallback with the frozen 45 x 10,000 / 37 x 20,000 topology, actual selected storage stack, original limits and real backend. Trap both reserved seeds and official artifact paths. Preserve raw logs/reports with exact source/platform/counter labels. Check generation, largest encoding, saved-file verification, file/namespace barriers, final close and capability issuance. Any unproved operation prevents official readiness.
7. **Independent exact-source review and attestation, then separate operator decision.** Complete ordinary CI, applicable Linux regressions and Windows proof; review protected hashes, commit-by-commit ancestry, failure evidence and unsatisfied limits. Finalize status documents before the reviewed source. Only an independently approved implementation plus an explicit one-shot decision can authorize a reserved draw. This document supplies neither.
